# `harness.lock`

The lockfile records an agent setup, pinned and hashed. [`hlock pin`](../guides/pin.md)
writes one from the setup you already have; [`hlock resolve`](../guides/resolve.md) writes
one from a search over your tasks, along with the evidence for choosing it. Don't edit it
by hand, and do commit it.

Empty values, tables, and lists are omitted from the examples below for brevity. `hlock show --json`
prints the complete file.

## Top-level keys

| Key | Description |
|---|---|
| `lock-version` | Schema version. This release reads and writes `1`. |
| `generated-by` | The `harness-lock` version that wrote the lock |
| `manifest-hash` | Hash of the `harness.toml` the lock was resolved from (for a pinned lock with declared dependencies, of its dependency sections only). Used by `hlock check`. |
| `kind` | `pin` for a [pinned lock](#pinned-locks), `localized` for a [localized one](#localized-locks), `migrated` for a [migrated one](#migrated-locks); absent for a resolved lock |

## Sections

| Section | Contents |
|---|---|
| `[stack]` | Stack name, and the `select` rule that chose it |
| `[[llm]]` | One entry per role: `provider`, `model`, the candidate string it came from, a `fingerprint`, and `params` |
| `[decision]` | Decision model `kind`, its `decisions`, and `thresholds` |
| `[harness]` | Harness `name` and `pattern`. For a harness with a profile, also the installed `version`, its install `source` (e.g. `brew-cask:claude-code@2.1.285`), and the `adapter` that ran the trials. |
| `[policy]` | `retries`, `max-steps`, `human-approval`, `risky-actions`, `tool-allowlist`, `sandbox` |
| `[context]` | Context `isolation` and `compaction` settings |
| `[[tool]]`, `[[skill]]`, `[[instructions]]` | MCP servers, skills, and instruction files, each with a source or digest. A pinned lock fills these in; see below. An `[[instructions]]` entry may have a `role` (`guardrails`, `memory`, `tool-guidance`) and `sections`, the roles it holds as `## Guardrails`-style sections |
| `[[subagent]]`, `[[script]]`, `[[middleware]]` | Subagent definitions, helper scripts, and middleware files (OpenCode plugin files, Codex's `.codex/hooks.json`): `name`, `path`, `digest`, `scope`, `vendored`, `format` (middleware), `source` (`tune` when an optimizer wrote it), and `scan`. See [Harness components](../guides/pin.md#harness-components) |
| `[[decider]]` | One per [decision model](../guides/deciders.md) the stack uses (see below) |
| `[evidence]` | `simulated = true` when an agent CLI's trials ran on the reference harness rather than the agent itself. The eval packs measured: their paths (`eval-pack`), `name@version` (`eval-pack-version`), and a digest of every file in them (`eval-pack-digest`), which `hlock check` compares with the packs on disk, warning when they've changed. Then the split measured (`holdout` when `resolve` checked the winner on it, with the search score kept as `success-rate.search`; `search` otherwise), the trial count, and success-rate, cost, and latency statistics. `[evidence.judge]` records the judge of [`judge` and `trace` graders](../guides/eval-packs.md#judges): its `model`, the model that `answered`, its `protocol`, a `fallback`, the share of `uncertain-grades`, and `cost-usd-per-task` when
the provider publishes a price. |
| `[verify]` | Runtime verification thresholds: `canary-tasks`, `min-success-rate`, `fingerprint-tolerance` |
| `[provenance]` | The backend that produced the lock, the search settings (`candidates`, the number of stacks; `trials` and `holdout-trials` run; `cached`, those reused), for a pinned lock the `scopes` it captured and any `user-include` patterns, and `openapm` (`"0.1"`) when APM packages were resolved |
| `[[package]]` | [APM packages](../guides/dependencies.md#apm-packages) declared dependencies resolved to (see below) |

## Pinned locks

[`hlock pin`](../guides/pin.md) writes a lock with `kind = "pin"`, no `manifest-hash`, and
no evidence. `[provenance] scopes` says what it captured: `["project"]` by default, or
`["project", "user"]` with `hlock pin --user` or `-i` (see
[Project and user scope](../guides/pin.md#project-and-user-scope)). With `-i`,
`[provenance] user-include` lists the patterns that picked the user-level items.
`hlock check` re-captures the same selection. A pinned lock without `scopes` was written before scopes existed and
captured both. Its `[[llm]]` entries may carry `endpoint` and `runtime`; `[[tool]]` entries for
MCP servers carry `transport`, `command`, `args`, `url`, `env`, `headers`, `scope` and
`enabled`; `[[skill]]` entries carry `scope`, `path` and `vendored`. It adds:

| Section | Contents |
|---|---|
| `[[native]]` | Plugins, packages, extensions and marketplaces: `kind` (e.g. `claude-code.plugin`, `pi.package`), `name`, `version`, `source`, `revision`, `integrity`, `enabled`, `config` |
| `[[runtime]]` | Inference runtimes: `name`, `location` (`local` or `network`), `version`, `source`, `endpoint`, and `[[runtime.model]]` entries with `id`, `source`, `revision`, `digest`, `size-bytes`, `present` |
| `[[config]]` | Harness config files: `id`, `path`, `format`, `restore` (`whole`, `pointers`, `record`), `pointers`, `digest`, `vendored` |
| `[[secret]]` | Placeholders that replaced secrets: `name` (the environment variable that supplies it) and `used-by` |

## Scans

Each `[[skill]]`, `[[instructions]]`, `[[config]]`, `[[subagent]]`, `[[script]]` and `[[middleware]]` entry has a `scan` key: the
[hidden-character scan](../guides/audit.md#hidden-characters) of what it places. `clean`;
`warnings:N` (invisible characters such as zero-width spaces); `critical:N` (characters that
hide text, which `sync` won't place); or `allowed:critical`, when they were let through on
purpose with `--allow-hidden` (and are placed only once they're approved on the machine, by
`hlock trust`). A lock without `scan` keys was written by an older hlock, and `hlock check`
scans it.

A `[[skill]]` entry also has `scripts`: the files in the skill's `scripts/` directory, which
run. `hlock trust` approves them by the skill's digest, and `sync` won't place a skill that
carries scripts its entry doesn't list. A lock without `scripts` was written by an older hlock:
a skill of it that isn't fetched yet is asked about, since what it runs can't be listed.

## Declared dependencies

A `[[skill]]`, `[[tool]]`, `[[instructions]]` or `[[native]]` entry that
[`hlock add`](../guides/dependencies.md) wrote, or that a `harness.toml` or `apm.yml`
declaration resolved to, has these keys besides its usual ones:

| Key | Description |
|---|---|
| `declared` | `true`: it's declared, not only found installed |
| `source` | The source as declared (`github:acme/skills/skills/sql@^1.2`). An `[[instructions]]` entry's `name` is where it's installed (`.claude/rules/style.md`) |
| `constraint` | The version range asked for (`^1.2`) |
| `resolved-tag`, `resolved-ref` | The tag a range matched, and the branch or tag the commit came from |
| `commit` | The git commit it's pinned to. `sync` fetches this commit and checks the entry's `digest`; the entry is never vendored |
| `version`, `integrity` | For an MCP server from npm or PyPI: the exact version and the package's integrity hash |
| `required-by` | For what a package brought in: the packages above it, the declared one first |
| `[skill.evidence]` (and `[tool.evidence]`, …) | What `hlock add --eval` measured: `eval-pack` (the packs' digest), `split`, `trials` per side, `baseline-success-rate`, `success-rate`, the cost of each, and the `digest` it measured. `check` reports it as stale when the digest changes |

A `[[package]]` entry records an APM package: its `name`, `source`, `digest` (the package
tree's hash, computed as APM computes `content_hash`), `depth` (1 for one the project
declares), its `apm.yml` `version` and `license`, what it held that hlock doesn't install
(`skipped`: prompts, agents, hooks), and the same `declared`, `constraint`,
`resolved-tag`, `resolved-ref`, `commit` and `required-by` keys.

## Localized locks

[`hlock localize`](../guides/localize.md) writes a lock with `kind = "localized"`,
`base-lock` naming the source lock, local `[[llm]]`/`[[runtime]]` entries, `[[config]]`
entries that point the harness at the local endpoint, and a `[localize]` table recording what
was replaced, the candidates considered, the memory budget, whether it was evaluated, and the
source lock's evidence as a baseline.

## Migrated locks

[`hlock migrate`](../guides/migrate.md) writes a lock with `kind = "migrated"`, `base-lock`
naming the source lock, the new `[harness]`, `[[skill]]` and `[[instructions]]` entries at
the paths the new harness reads (with a `vendored` copy under `.hlock/vendor/<harness>/migrate/<lock>/`
when they moved), `[[decider]]` wiring for its hooks, a `[[config]]` entry that sets its model
and MCP servers, and a `[migrate]` table: the harness it came from, how many of each part
carried over, what was replaced, notes on what didn't carry, and the source's evidence as a
baseline. Its own `[evidence]` is empty until you resolve it.

## `harness.tune.lock`

[`hlock tune`](../guides/tune.md) writes a separate tune lock with the same shape,
plus what tuning produced: the chosen hyperparameters, applied prompts, fine-tune
adapters, the data split, and the budget, all content-addressed. Adopt it into
`harness.lock` with `hlock tune apply`, which keeps the old lock in `harness.lock.prev`.

When the [optimize stage](../guides/tune.md#tune-the-harness-text) ran, `[tune.optimizer]`
records the optimizer, the `backend` that hosted its search, what it could edit, its budget
and usage, and a digest of the splits;
`[tune.acceptance]` records the noise band, the paired test run (`base`, `candidate`,
`better`, `worse`, `p`) and its cost, and why edits weren't accepted. Each accepted edit is
a `[[tune.edit]]` (`component`, `kind`, `op`, `before`, `after`, `path`, `rationale`), and
the lock's `[[instructions]]` (with `source = "tune"`) or `[[skill]]` entry points at its
file under `.hlock/tuned/`.

## `harness.meta.lock`

[`hlock meta pin`](../guides/meta.md) writes the meta harness's lock: a pinned lock
(`kind = "pin"`) of hlock's built-in agent, or of an installed harness's own config root.
See the [`harness.meta.toml` reference](meta-manifest.md#harnessmetalock) for what it
records.

## `harness.lock.prev`

[`hlock upgrade --apply`](../guides/upgrade.md) saves the previous lock here so
`hlock upgrade --rollback` can restore it. You can commit it or ignore it.

## `[[decider]]`

| Key | Description |
|---|---|
| `use` | What it decides: `approve`, `stop`, `route`, `tool` |
| `provider`, `model` | The decision model, as the provider names it |
| `protocol` | `systemone` or `decisions` |
| `endpoint`, `key-env` | Where it's reached, and the variable its API key is read from. Used only when they're on this machine, the provider's own, or what your `harness.toml` sets ([why](../guides/deciders.md#locks-from-someone-else)) |
| `runtime` | The local runtime serving it (`ollama`, `ollaya`) |
| `resolved-from` | The `harness.toml` reference it came from, or the harness setting `pin` read |
| `via` | `hook` (hlock wires it in), `native` (a setting of the harness's own), `env` (code harnesses), `simulated` (the reference harness) |
| `[[decider.wiring]]` | Where it's wired: the profile's `file` and the harness `event` |
| `may`, `min-probability`, `timeout-ms` | What it may answer, how sure it must be, how long a hook waits |
| `questions` | A digest of hlock's questions for the use; a newer hlock with other questions is drift |
| `[decider.policy]` | The policy file's `path` and `digest` |

## Checks

A lock can come from someone else's repository ([`hlock pull`](../guides/pull.md)), so hlock
checks every lock it reads, before using any of it, for values that become paths or
command-line words:

| Value | Must be |
|---|---|
| `[harness] name`, `[[skill]] name` | A plain name: no `/`, `\`, or `..` |
| `vendored` (skills, instructions, config), `[decider.policy] path` | A relative path inside the project: no leading `/`, no `..` |
| `[harness] version`, `[[native]] version`, `[[runtime]]` `name`, `version`, and each model's `id`, `source` and `revision`, `[[llm]] runtime`, `[[decider]]` `model`, `runtime` and wiring `event` | Letters, digits and `._:/@+-`, not starting with `-` |
| `[[decider]] use` | `approve`, `stop`, `route`, or `tool` |

A lock that fails a check isn't read: the error names the field. hlock writes locks
atomically (a temporary file, then a rename), and leaves out JSON `null`s, which TOML
can't hold.
